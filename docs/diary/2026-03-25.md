# 2026-03-25 Research Diary

## Summary
Today the project moved from “Phase 1 is closed enough” to “Phase 2 has started in the main workspace.” The main new capability is a minimal sticky replanner: keep shard ownership unchanged when the current placement still fits, and only fall back to static redistribution when it no longer fits. We also clarified that the current move-cost model is intentionally temporary and listed the factors a more realistic cost model should include later.

## Decisions made

### 1. Start Phase 2 with the smallest useful rebalancing rule
The first Phase 2 rule is:

> keep current shard ownership when it still fits; otherwise fall back to static redistribution

This is deliberately smaller than a full migration-aware planner. The goal is to get one verifiable smart-planning step into the main workspace before building reconfiguration diffs, join/leave handling, or transport-driven cluster migration.

### 2. Treat the current move-cost function as a heuristic, not a final model
The current `score_assignment_move_cost(...)` is still only:

- same owner → `0.0`
- unknown owner → `1.0`
- moving shard → `10.0 + shard_width`

This is enough to encode “prefer not moving shards,” but it is not a physically meaningful cluster cost model yet.

### 3. Record the future cost-model inputs explicitly
The next-generation cost model should consider at least:

- node quality / device quality
- actual shard parameter size
- bandwidth between nodes
- whether the target node already has the shard loaded
- device type (`CPU` / `GPU`)
- load / unload time
- special costs for first / last shard roles

These are now part of the documented experiment direction, not just an informal note.

### 4. Tighten documentation workflow
Project rules now explicitly say that after any important architectural decision or major code update, the agent should:

- update the relevant README(s)
- append the experiment/research note to the current daily diary

This is intended to keep the “current state” docs and the “research trail” in sync.

## Addendum — DP cold start and boundary-adjusting replan replaced the old planner model

### Summary
The planner direction changed materially today. The repo no longer treats “average continuous split by compute score” as the intended cold-start logic, and it no longer treats replanning as a fixed-boundary owner-reassignment problem. The current direction is now explicit: cold start uses a contiguous-partition DP over heterogeneous node quality, and replanning is allowed to move boundaries while charging migration and instability penalties.

### Decisions made
The first architectural decision was to separate node information into an explicit inventory layer. `inference/NodeInventory.py` now defines `NodeState` and `ClusterState`, and the planner consumes normalized node state instead of ad-hoc raw profile fields. The second architectural decision was to treat local-network deployment as the v1 assumption. That means link bandwidth and latency stay in the data model for future work, but they do not dominate the v1 cold-start objective. The third architectural decision was to make cold start bottleneck-oriented: use DP to minimize the slowest contiguous stage rather than trying to equalize layer counts. The fourth architectural decision was to let replanning move boundaries. Join/leave behavior was judged too constrained under the old fixed-boundary rule, so the replanner now solves a boundary-adjusting DP with migration and instability terms instead of only changing owners inside pre-existing shard ranges.

## Addendum — the planner demo is now interactive and stateful

### Summary
The demo has been upgraded from a pre-rendered scenario printer into an interactive cluster simulator. Instead of hard-coding A/B/C snapshots, it now starts from four candidate nodes, lets the user choose any initial active subset, and then applies `join` / `drop` commands against a persistent session state.

### Decisions made
The most important change was to treat `loaded_shards` as session state, not as scenario text. When a node receives a shard in a replanned placement, that range is merged into the node’s stored `loaded_shards`; if that node stays around for later replans, the later planner sees the inherited load state. This was necessary because the previous version made the leave scenario misleading: node `d` looked cold again even though it had already loaded work in the join scenario.

The second change was to make the script user-driven. The current command set is intentionally small: `start`, `join`, `drop`, `show`, `help`, and `quit`. That is enough to demonstrate continuous cluster evolution without turning the script into a full TUI.

After switching to the interactive version, one more state-model bug showed up: `start` was reusing the existing session and accumulating old loaded ranges, which made repeated starts look nonsensical. That has now been corrected. `start` resets to the baseline candidate-node state, active nodes show only their current loaded shard ranges, and invalid commands return a readable error instead of surfacing a raw exception.

## Addendum — placement metric rigor now has a frozen vocabulary

### Summary
Before changing coordinator math, the project now freezes three terms so future metric work does not drift. `NodeState` remains the canonical node model, the primary optimization objective is estimated bottleneck stage time, and future byte-based capacity modeling will be described as a calibrated approximation rather than a precise physical model.

### Decisions made
The plan originally suggested introducing a `NodeCapability` peer type. That direction was rejected for now because it would compete with `NodeState` and make the source of truth ambiguous. The metric stack will instead be built as derived helpers on top of `NodeState`. The coordinator metric will be plan-aware when a `PlacementPlan` exists and fall back to a reference-slice estimate otherwise. The docs now also explicitly say that LAN is still the current assumption, so network cost is not yet the primary term.

### Code or docs changed
- `docs/plans/2026-03-25-placement-metric-rigor.md`
- `inference/README.md`
- `docs/README.md`

Pipeline ordering now also uses the shared reference stage-time metric instead of the old effective_speed × capacity product heuristic. Nodes are ordered directly by estimated stage time for a reference slice width, with capacity and node_id only used as deterministic tie-breakers.

## Addendum — CPU hardware scanning now produces usable local node snapshots

### Summary
The local hardware scan path was still effectively GPU-biased. CPU hosts were technically supported, but on macOS the available-memory estimate only used `Pages free` from `vm_stat`, which made the machine look almost full and collapsed `effective_capacity_blocks` to zero. That has now been corrected.

### Decisions made
The key decision was to keep the CPU path dependency-free and improve the existing native probes instead of pulling in a new system package. For Darwin hosts, available memory is now estimated from `Pages free + Pages inactive + Pages speculative + Pages purgeable`, using the page size reported by `vm_stat`. This is still an approximation, but it matches the planner’s calibrated-capacity philosophy much better than the previous near-zero free-page reading.
