## Decisions made

### 1. Lazy loading must use a meta-device shell, not `from_config().to(device)`
**Decision:** Keep the plan's true lazy-loading path:
- create an empty shell with `with torch.device("meta")`
- read only the needed safetensors keys
- materialize owned components with `load_state_dict(assign=True)`

**Why:** `from_config().to(device)` allocates the full model before weights are selectively assigned, which defeats the memory-saving goal for large models.

**Current direction:** This is the active implementation in `ShardLoader`.

---

### 2. Qwen `rotary_emb` must be rebuilt on the target device
**Decision:** Do not move Qwen's model-level `rotary_emb` out of the meta shell with `.to(device)`. Instead, rebuild it from `model_config` on the destination device.

**Why:** `Qwen2RotaryEmbedding` is a computed module rather than a normal safetensors-backed weight holder. Its internal buffers are not stored in safetensors, so moving it out of a meta shell triggers a meta-tensor error.

**Practical effect:**
- layers / embeddings / norm / lm_head still follow the lazy-loading plan
- only `rotary_emb` is treated as a computed special case

**Current direction:** Active and verified on the Qwen path.

---

### 3. Qwen last shard must still load embedding weights for weight tying
**Decision:** Keep loading `model.embed_tokens.weight` on the last shard when needed for `lm_head` weight tying.

**Why:** Qwen ties `lm_head.weight` to `embed_tokens.weight`, and the safetensors files may not contain an independent `lm_head.weight` entry.

**Current direction:** Active in `ShardLoader`.

## Addendum — Local `unsloth` Llama snapshot is usable, but reveals a real plan divergence

### New finding
The local snapshot at:
- `~/.cache/huggingface/hub/models--unsloth--Llama-3.2-1B-Instruct/snapshots/5a8abab4a5d6f164389b1079fb721cfab8d7126c`

is usable as a local model source for testing.

### Evidence
Confirmed locally:
- `config.json` loads with `AutoConfig`
- config class is `LlamaConfig`
- `num_hidden_layers = 16`
- `hidden_size = 2048`
- `tokenizer.json` / tokenizer config load successfully
- `model.safetensors` exists and exposes standard Llama layer keys

### Important divergence from the earlier assumption
The current code and notes assumed:
- Qwen uses model-level `rotary_emb`
- Llama computes RoPE only inside each layer and does not need model-level position embeddings

The local experiment showed this is not true for the current `transformers`/Llama implementation being exercised here.

Observed facts:
- the instantiated Llama model **does have** `model.rotary_emb`
- `LlamaDecoderLayer.forward(...)` accepts `position_embeddings`
- `LlamaAttention.forward(...)` tries to unpack `position_embeddings` as `(cos, sin)`
- running the current Llama shard pipeline fails with:
  - `TypeError: cannot unpack non-iterable NoneType object`

### What this means
This is a genuine cross-family / cross-implementation interface finding:
- Llama cannot safely be modeled as "rotary_key=None and layers fully handle RoPE internally" in the current environment
- the loader/forward abstraction likely needs to become more capability-driven than a simple family-level branch

### Practical recommendation
Do not blindly continue past Task 4.
First decide how to update the plan/code contract for rotary handling, then implement and verify that change before moving on.
