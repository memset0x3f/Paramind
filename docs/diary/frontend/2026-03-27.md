## Bug log

### 1. DM 接受后，发起方不能自动进入正式 DM
- Symptom: A 发起私聊，B 接受后，A 仍停在原会话，必须手动刷新才会进入正式 DM。
- Root cause: `dm.accepted` 事件最初被记录在目标 DM conversation 的 `conversation_id` 上；A 当时连着 `general` 的 stream，所以收不到这个事件。
- Fix: 把 `dm.requested / dm.accepted / dm.rejected` 视为全局事件，记录为 `conversation_id=None`；前端继续在 `dm.accepted` 时调用自动进入 DM 的切换逻辑。
- Verification: `test_dm_request_accept_flow_creates_single_dm_conversation` 增加了 stream 级断言；双实例实测时，接受后发起方会立刻发起 DM 的 messages/stream 请求。
- Remaining limitation: `conversation.deleted` 等其它全局 UI 生命周期事件仍建议未来统一收进单独全局事件流。

### 2. 退出 DM 后，对端不一定立刻回到“请求私聊”
- Symptom: 其中一方退出 DM 后，另一方有时仍保留旧 DM 或 Peer 卡动作未及时重置。
- Root cause: 退出操作最初只是前端本地切走，没有一个明确的 backend 级 conversation 生命周期删除事件。
- Fix: 增加 `/api/conversations/{conversation_id}/leave`，在 desktop backend 删除 DM conversation 并广播 `conversation.deleted`；前端收到后移除会话并回退到 `general` 或其它非 request 会话。
- Verification: `test_leaving_dm_removes_conversation_for_both_peers` 通过；双实例手测中退出后双方 DM 都会被清掉。
- Remaining limitation: `conversation.deleted` 目前仍沿 conversation 维度传播，后续应一起纳入真正的全局事件流。

### 3. 左侧会话栏在新消息和 AI 流式生成时反复闪烁
- Symptom: 新消息到达或 AI draft 流式更新时，左侧整列会像重新加载一样闪烁。
- Root cause: renderer 早期实现大量依赖 `renderAll()`、`innerHTML=''`、`replaceChildren(...)` 和 conversation 级全量签名比较；local draft 还会错误更新会话摘要。
- Fix: 左侧改为 keyed patch，按 conversation id 复用节点，只 patch 单卡内容；local draft 不再更新 `conversation.updated_at / last_message / conversation.updated`。
- Verification: 前端状态测试覆盖了 preview 截断和最小 render scope；双实例手测时，AI draft 流式期间左侧不再显示草稿内容。
- Remaining limitation: 仍有 renderer 历史代码使用整块重绘路径，后续应进一步拆成真正的全局事件流 + 分区 patch。

### 4. `@AI` 第一轮经常卡在“生成中”，点重试才出结果
- Symptom: 首次 `@AI` 请求时 draft 长时间不出字，点一次重试反而正常。
- Root cause: 两个问题叠加：前端首轮 stream 从 `after=0` 吃 backlog；模型第一次请求时还在冷启动加载。
- Fix: bootstrap 暴露 `latest_event_id`，首轮 stream 从最新事件游标开始；desktop inference runner 启动即预热模型，减少首轮冷启动等待。
- Verification: 增加 bootstrap cursor 和 inference runner 回归测试；新实例中首轮 stream 参数不再从 `0` 开始。
- Remaining limitation: 如果首次需要从 HF 下载模型文件，仍可能有一次性等待。

### 5. AI draft 看起来不是流式，而是最后一下才完整出现
- Symptom: Draft 经常在“生成中”停很久，随后一次性出现完整文本。
- Root cause: 前端同时处理 `message.token` 和 `message.updated`，但一度采用“token 盲 append + updated 只改状态”的混合策略；事件顺序交错时会丢增量。
- Fix: 流式 draft 的内容节点统一以当前累计 `message.content` 为权威来源；`message.updated(streaming)` 也直接 patch 内容，`appendTokenToDraft()` 只负责把当前累计内容写回节点。
- Verification: `test_chat_state.mjs` 的 token 增量测试持续通过；最新 Electron 手测中 draft 文本逐步增长。
- Remaining limitation: 仍建议以后补更明确的全局/会话事件拆分，减少 token 与 updated 两路合并的复杂度。

### 6. AI 真实推理曾输出“我是 + 一串空格”
- Symptom: 模型首词正常，随后只输出空格，导致看起来像流式卡死。
- Root cause: 自定义推理层的 KV cache 增量解码接口参数与当前 Transformers/Qwen2 API 不匹配，`past_key_values` / `cache_position` 传递错误。
- Fix: 修正 `/inference/ShardLoader.py` 中 layer forward 的 cache 参数对齐。
- Verification: cache 开/关时输出恢复一致；修复后可正常生成完整句子。
- Remaining limitation: 这属于 inference 层问题，但对前端“流式是否正常”有直接观感影响，所以保留在此记录中。

### 7. 消息时间显示成 UTC（例如 05:01）
- Symptom: 本地看到的消息时间直接显示成 UTC，而不是用户设备当前时区时间。
- Root cause: 前端直接用 `new Date(...).toLocaleTimeString()`，但没有统一时区策略；曾短暂尝试写死香港时区，后来确认这也不对。
- Fix: 抽出统一的 `formatClockTime(...)`，默认读取当前用户设备的 `Intl.DateTimeFormat().resolvedOptions().timeZone`；测试里才显式传时区。
- Verification: `test_chat_state.mjs` 增加时间格式测试；运行时显示会跟随设备本地时区。
- Remaining limitation: 目前还没有提供用户手动覆盖时区的设置项。


### 8. 发起私聊后，左侧不会立刻出现 pending DM 卡片
- Symptom: 点击“请求私聊”后，左侧列表不会立刻出现新的 pending DM 卡片，往往要手动刷新后才看见。
- Root cause: `requestDirectMessage()` 只更新了本地 `dmRequestsById` 然后直接切换 active conversation，但没有立即 patch 左侧 conversation list 与右侧 Peer 关系状态；这一条本地创建路径没有等到 global event 到来前的即时 UI 更新。
- Fix: 在本地创建 DM request 成功后，立即 `upsertRelationship(...)`，并同步调用 `renderConversations()` 与 `renderPeers()`，再切到 request 会话。
- Verification: 代码路径已改为本地 request 成功即 patch 左右两侧；`node --check` 通过。
- Remaining limitation: 这仍是 renderer 层即时 patch；更彻底的方案仍然是让 lifecycle UI 完全收口到稳定的 global stream 驱动。


### 9. 双实例消息顺序会倒置，晚发的消息可能排到前面
- Symptom: 两个实例之间聊天时，后发送的消息有时会出现在更早的位置，看起来像双方“时钟不统一”。
- Root cause: 前端按 `created_at` 排序消息，但 remote message 落库时没有保留发送端的 `created_at / updated_at`，而是使用接收端本地插入时间；同时 remote conversation 的 `updated_at` 也曾使用接收端本地时间。这样一来，排序依据在两端不一致。
- Fix: backend 在 `_apply_remote_message_event()` 中显式保留发送端消息的 `created_at / updated_at`，并用远端时间更新 conversation；序列化 datetime 时对 SQLite 取回的 naive UTC 时间统一补回 `+00:00`。
- Verification: 新增 `test_remote_message_sync_preserves_source_timestamps`，验证 remote message 与 source message 的时间戳一致，并且 remote conversation 的 `updated_at` 与 source conversation 一致。
- Remaining limitation: 当前排序仍主要依赖时间戳，而不是全局单调的会话内序号；若未来要支持真正跨机器 P2P，最好进一步引入更稳定的 per-conversation ordering key。
