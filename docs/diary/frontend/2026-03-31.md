## Timeline message reorder bug

- **Symptom:** In the desktop timeline, messages could appear out of chronological order even though backend timestamps were correct; a later-created local/user card could stay above earlier peer/AI cards.
- **Root cause:** `/Users/acropolis/Github_Project/Paramind/paramind/apps/desktop/renderer/chat.js` patched existing message nodes in place but did not reliably reorder cached timeline DOM nodes after insertion/update. The cached pane could preserve stale node order even when chronological order changed.
- **Fix:** Added a renderer regression test in `/Users/acropolis/Github_Project/Paramind/test/backend/test_renderer_harness.spec.mjs` and updated the timeline patch path to assign each message node a stable timestamp sort key, then reorder cached timeline nodes by that key after insert/update/remove.
- **Verification:** `cd /Users/acropolis/Github_Project/Paramind/paramind/apps/desktop && npx playwright test test_renderer_harness.spec.mjs -g "existing timeline nodes are reordered when a message update changes chronological position"`, plus full `make test-frontend-fast`
- **Remaining limitation:** Ordering is still timestamp-based; if future distributed delivery needs stronger guarantees than timestamp order, the renderer should eventually sort by an explicit per-conversation sequence key instead of timestamps alone.

## Global lifecycle stream startup bug
- **Symptom:** group participant counts, DM review cards, and DM accept/reject state sometimes stayed stale until the user manually clicked refresh.
- **Root cause:** `/Users/acropolis/Github_Project/Paramind/paramind/apps/desktop/renderer/chat.js` was awaiting `openConversationStream()` inside `refreshBootstrap()` and `selectConversationWithOptions()`, and awaiting `openGlobalStream()` in `init()`. Those stream functions are effectively long-lived loops, so awaiting them blocked later startup work — especially the global shell stream that drives DM/group lifecycle updates.
- **Fix:** changed those call sites to fire the stream tasks without awaiting them, so bootstrap/UI setup can finish and the global lifecycle stream can start in parallel with the active conversation stream.
- **Verification:** `make test-frontend-fast`, plus new Playwright regression coverage for dynamic pending-DM accept/reject and active group participant metadata updates.
- **Remaining limitation:** the renderer still depends on fetch-based long-lived streams; if we want stronger resilience later, we should add explicit reconnect/backoff instead of relying only on initial startup success.

## Group accept shell update and sidebar flicker follow-up
- **Symptom:** Group participant counts could still fail to update immediately on accept for the inviter side, and sidebar updates could still visually churn when only preview text changed.
- **Root cause:** The renderer handled `group.accepted` mainly as invitation cleanup and only relied on a later `conversation.updated` to refresh active group metadata, so real-time UI depended on event ordering. Separately, sidebar cards were still patched by replacing `innerHTML`, which recreated child nodes on each preview/badge change and amplified visible flicker.
- **Fix:** Reused the existing Playwright harness suite to add a direct `group.accepted` regression and a DOM node reuse regression. Updated `/Users/acropolis/Github_Project/Paramind/paramind/apps/desktop/renderer/chat.js` so `group.accepted` immediately `upsertConversation(...)` when a conversation payload is present, and changed conversation card patching to preserve the existing node structure while mutating title/subtitle/kind/unread text in place.
- **Verification:** `cd /Users/acropolis/Github_Project/Paramind/paramind/apps/desktop && npx playwright test /Users/acropolis/Github_Project/Paramind/test/backend/test_renderer_harness.spec.mjs`, `cd /Users/acropolis/Github_Project/Paramind && make test-frontend-fast`
- **Remaining limitation:** If any flicker remains in the real Electron shell after these DOM-stability fixes, the remaining source is likely narrower than the prior broad rerender paths and will need another targeted reproduction.
